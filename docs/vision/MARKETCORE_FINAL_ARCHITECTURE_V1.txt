6. РЕЖИМЫ АВТОНОМНОСТИ

MarketCore поддерживает три режима.

----------------------------------------------------------

MODE 1

MONITOR

Система:

- собирает данные;
- измеряет KPI;
- выявляет отклонения;
- определяет узкие места;
- не выполняет управляющие действия.

----------------------------------------------------------

MODE 2

RECOMMEND

Система:

- формирует решение;
- оценивает ожидаемый эффект;
- рассчитывает confidence;
- объясняет причины;
- предлагает действие оператору;
- ожидает подтверждения.

----------------------------------------------------------

MODE 3

AUTONOMOUS

Система:

- выполняет только заранее разрешенные
  классы действий;
- обязательно проходит Policy Engine;
- обязательно проходит Risk Engine;
- сохраняет полный audit trail;
- поддерживает rollback;
- не получает неограниченное право
  на торговые действия.

==========================================================

7. ПОЛИТИКА АВТОНОМНОСТИ

Режим системы и право выполнить действие
не являются одним и тем же.

Каждое действие классифицируется отдельно.

Примеры действий,
которые могут быть разрешены автономно:

- изменить приоритет Research;
- запустить повторное исследование;
- расширить исследовательскую выборку;
- запустить дополнительный Paper;
- остановить неуспешный эксперимент;
- перераспределить исследовательские ресурсы.

Действия,
которые по умолчанию не разрешаются автономно:

- включение реальной торговли;
- отправка реальных заявок AI-слоем;
- увеличение лимитов риска;
- отключение kill switch;
- изменение базовой Risk Policy;
- перевод кандидата напрямую в Live;
- обход обязательных governance-проверок.

==========================================================

8. POLICY ENGINE

Policy Engine определяет:

- разрешен ли класс действия;
- в каком режиме он допустим;
- требуется ли подтверждение оператора;
- какой Risk Guard применяется;
- необходим ли дополнительный эксперимент;
- допустим ли rollback;
- срок действия разрешения;
- максимальный масштаб действия.

Любой отказ Policy Engine логируется.

==========================================================

9. CONFIDENCE ENGINE

Confidence не заменяет Policy Engine.

Confidence Engine оценивает:

- качество данных;
- объем выборки;
- устойчивость результата;
- воспроизводимость;
- regime stability;
- статистическую неопределенность;
- расхождение Research / Paper / Runtime;
- историю аналогичных решений;
- результат предыдущих действий.

Высокий confidence
не дает права обойти Policy Engine.

==========================================================

10. HYPOTHESIS ENGINE

Hypothesis Engine формирует
гипотезы улучшения Profit Factory.

Примеры:

- исследовать новый инструмент;
- изменить приоритет стратегии;
- увеличить выборку;
- проверить новый timeframe;
- провести повторную robustness-проверку;
- изменить исследовательский фильтр;
- остановить слабое направление;
- запустить контролируемый эксперимент.

Каждая гипотеза должна содержать:

- hypothesis_id;
- цель;
- основание;
- ожидаемое влияние на Profit;
- ожидаемое влияние на Risk;
- confidence;
- стоимость проверки;
- критерий успеха;
- критерий остановки;
- rollback plan.

==========================================================

11. IMPROVEMENT ENGINE

Improvement Engine:

- определяет главное ограничение;
- ранжирует гипотезы;
- оценивает Profit Impact;
- оценивает Risk Impact;
- выбирает допустимое действие;
- инициирует эксперимент;
- оценивает фактический эффект;
- обновляет Strategy Memory.

Главный вопрос:

Какое изменение сегодня
даст максимальный прирост
ожидаемой устойчивой прибыли
при допустимом риске?

==========================================================

12. STRATEGY MEMORY

MarketCore сохраняет историю решений.

Для каждого решения:

- decision_id;
- hypothesis_id;
- timestamp;
- инициатор;
- режим автономности;
- входные данные;
- примененные KPI;
- причина;
- ожидаемый эффект;
- confidence;
- policy verdict;
- risk verdict;
- действие;
- фактический эффект;
- отклонение от ожиданий;
- вывод;
- статус гипотезы;
- rollback status.

Strategy Memory используется
для будущей оценки решений,
но не может напрямую отправлять заявки.

==========================================================

13. EXPERIMENT ENGINE

Если данных недостаточно,
система не должна выдавать
предположение за подтвержденное решение.

Она должна создавать эксперимент.

Эксперимент обязан иметь:

- ограниченный scope;
- контрольную группу;
- тестовую группу;
- фиксированный период;
- критерии успеха;
- ограничения риска;
- stop conditions;
- audit trail;
- rollback.

Эксперименты сначала выполняются
в Research или Paper.

Live-эксперименты требуют
отдельного допуска.

15. OPERATOR WORKSPACE

Operator Workspace должен отвечать
не только на вопрос:

Что произошло?

Он должен отвечать:

1. Зарабатывает ли система?

2. Где теряется потенциальная прибыль?

3. Почему возникло ограничение?

4. Какое действие даст
   максимальный ожидаемый эффект?

5. Может ли действие быть выполнено
   автоматически?

6. Каков фактический эффект
   предыдущего решения?

16. PRESENTATION

Presentation Framework V1
считается зафиксированным.

Обязательные требования:

- RenderTree;
- доменные Node Types;
- сериализация;
- validator;
- Browser RenderTree Executor;
- Browser DOM Driver;
- i18n;
- platform-neutral domain model.

Запрещено:

- серверное построение интерфейса через HTML;
- HTML-типы внутри RenderTree;
- hardcode пользовательских текстов;
- hardcode управляемых параметров;
- бизнес-логика в DOM Driver;
- SQL в Presentation;
- trading actions из UI.

Статический bootstrap shell
может существовать только как
минимальная точка загрузки Runtime.

Он не является шаблоном экрана
и не содержит бизнес-данных.

==========================================================

17. I18N

Все пользовательские тексты:

- хранятся через message keys;
- не встраиваются в доменные Node Types;
- не хардкодятся в presenter/renderer;
- поддерживают минимум ru-RU;
- допускают расширение локалей;
- имеют fallback policy;
- проходят проверку отсутствующих ключей.

Доменные коды и статусы
не должны зависеть от языка интерфейса.

23. ОСНОВНОЙ КРИТЕРИЙ НОВОЙ ФУНКЦИИ

Новая функция имеет высокий приоритет,
если она:

- увеличивает ожидаемую прибыль;
- увеличивает вероятность получения прибыли;
- снижает риск потери прибыли;
- сокращает время принятия решения;
- повышает качество решения;
- устраняет bottleneck;
- повышает воспроизводимость результата;
- улучшает управляемость автономности.

Если связь с этими результатами
не доказана,

функция имеет низкий приоритет.
