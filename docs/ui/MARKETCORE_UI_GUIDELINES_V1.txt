==========================================================
MARKETCORE_UI_GUIDELINES_V1
Стандарт проектирования интерфейса MarketCore Workspace V2
==========================================================

Статус документа: ОБЯЗАТЕЛЬНЫЙ СТАНДАРТ
Версия: V1
Язык документа: русский
Назначение: единые правила проектирования UI/UX для MarketCore Workspace V2

==========================================================
1. ЦЕЛЬ ИНТЕРФЕЙСА
==========================================================

Интерфейс MarketCore предназначен не для отображения технических таблиц, а для управления состоянием проекта.

Главная задача интерфейса:

- показать, где сейчас находится система;
- объяснить, что работает;
- объяснить, что заблокировано;
- показать причину блокировки;
- показать следующее действие;
- дать быстрый переход к деталям.

MarketCore Workspace V2 должен быть рабочим местом оператора, аналитика и руководителя проекта, а не набором отдельных страниц.

==========================================================
2. БАЗОВЫЕ ПРИНЦИПЫ
==========================================================

1. Workspace вместо набора страниц.

2. Главное состояние проекта должно быть понятно за один взгляд.

3. Критически важная информация должна быть доступна максимум за два клика.

4. Mobile First:
   сначала проектируется телефон,
   затем планшет,
   затем desktop.

5. Телефон — это самостоятельный интерфейс, а не уменьшенная копия desktop.

6. Интерфейс не должен показывать внутренние коды системы.

7. Все тексты должны проходить через i18n.

8. Все цвета, размеры, отступы и состояния должны быть централизованы.

9. UI не содержит бизнес-логики.

10. Backend ядра не переписывается ради UI.

==========================================================
3. ЛУЧШИЕ ПРАКТИКИ, КОТОРЫЕ ИСПОЛЬЗУЕМ
==========================================================

Информационная архитектура:
- Bloomberg Terminal.

Рабочее пространство и навигация:
- JetBrains IDE.

Карточки, графики и мобильность:
- TradingView.

KPI, health-панели и мониторинг:
- Grafana.

Мы не копируем внешний вид этих систем.
Мы используем их лучшие принципы.

==========================================================
4. ПРАВИЛО 3 СЕКУНД
==========================================================

Первый взгляд — до 3 секунд.

Пользователь должен понять:

- общее состояние проекта;
- статус Production;
- главный риск;
- следующее действие.

Пример:

Исследование
Production заблокирован
Причина: недостаточно статистики
Далее: продолжать Paper

==========================================================
5. ТРИ УРОВНЯ ИНФОРМАЦИИ
==========================================================

Уровень 1. Первый взгляд.

Показывает только состояние и действие.

Пример:
- Исследование
- Бумажная проверка завершена
- Production заблокирован
- Далее: накопить статистику

Уровень 2. Второй взгляд.

Показывает KPI.

Пример:
- Кач. модели: 100%
- Готовн.: 51%
- Устойчив.: 51%
- Сделки: 3

Уровень 3. Детали.

Открывается по нажатию.

Пример:
- таблицы;
- журналы;
- причины;
- диаграммы;
- история;
- диагностические данные.

==========================================================
6. ИНФОРМАЦИОННАЯ АРХИТЕКТУРА WORKSPACE V2
==========================================================

Обязательные зоны:

1. Mission Control
   Главный экран состояния проекта.

2. Portfolio
   Капитал, позиции, PnL, комиссии, риск, экспозиция.

3. Paper
   Бумажная проверка, сделки, аналитика, устойчивость.

4. Runtime
   Текущие процессы и сервисы.

5. Research
   Исследовательские кандидаты.

6. Knowledge
   Знания о рынке, структура, контексты, источники.

7. Edge
   Оценка преимущества.

8. Logs
   Журналы и диагностика.

9. Settings
   Настройки и параметры.

==========================================================
7. MISSION CONTROL
==========================================================

Mission Control — первый экран.

Он отвечает на вопросы:

- где мы;
- что работает;
- что заблокировано;
- почему заблокировано;
- что делать дальше.

На Mission Control запрещено показывать:

- SQL;
- сырые payload;
- внутренние коды;
- длинные таблицы;
- технические идентификаторы без необходимости.

==========================================================
8. MOBILE FIRST
==========================================================

Телефонный интерфейс должен быть спроектирован отдельно.

Требования:

- одна колонка;
- крупные карточки;
- минимум текста;
- touch-элементы не менее 44 px;
- понятные сокращения;
- нижняя или боковая навигация;
- ключевой статус виден без прокрутки;
- длинные таблицы заменяются карточками или диаграммами.

На телефоне не должно быть ощущения "уменьшенного desktop".

==========================================================
9. ЕСТЕСТВЕННЫЕ СОКРАЩЕНИЯ
==========================================================

Используем русские и понятные сокращения.

Предпочтительно сокращать слова естественно, с точкой, а не создавать искусственные аббревиатуры.

Правильно:
- Кач. модели
- Готовн.
- Устойчив.
- Доверие
- Покрытие
- Прод.
- Приб. сделки
- Убыт. сделки
- Ожид.
- Просадка

Нежелательно:
- КМР
- ГО
- УМ
- ДЗ
- ПП
- ГП

Исключения допускаются только для общепринятых профессиональных терминов:

- PnL
- ATR
- VWAP
- RSI
- MACD
- MAE
- MFE

Для каждого сокращения должна быть доступна расшифровка:
- по нажатию;
- по наведению;
- в деталях карточки.

==========================================================
10. ТРИ ВАРИАНТА ПРЕДСТАВЛЕНИЯ ТЕРМИНА
==========================================================

Для каждого важного термина должны быть три формы:

1. Полная — desktop.
2. Короткая — планшет.
3. Мобильная — телефон.

Примеры:

Полная:
Качество модели рынка

Короткая:
Кач. модели

Мобильная:
Кач. мод.

Полная:
Готовность к обучению

Короткая:
Готовн.

Мобильная:
Готовн.

Полная:
Устойчивость модели

Короткая:
Устойчив.

Мобильная:
Устойчив.

==========================================================
11. I18N
==========================================================

Все строки интерфейса должны проходить через i18n.

Запрещено выводить в UI:

- внутренние коды;
- названия таблиц;
- технические ключи;
- resource_key;
- strategy_code;
- source_version;
- raw payload.

Примеры запрещенного вывода:

RSI_MEAN_REVERSION_V1
paper.feedback.reason.low_sample_size
marketcore_ui.capital_summary_v1
TRADING_PLAN_PARAMETER_BUILDER_V1

Вместо этого:

Возврат к среднему RSI
Недостаточно данных
Сводка капитала
Построение торгового плана

==========================================================
12. СТРАТЕГИИ
==========================================================

Стратегии должны отображаться через словарь.

Пользователь не должен видеть внутренний код стратегии.

Пример:

Внутренний код:
RSI_MEAN_REVERSION_V1

Название в UI:
Возврат к среднему RSI

Короткое:
RSI возврат

Мобильное:
RSI

Описание:
Стратегия ищет возврат цены к среднему значению после отклонения.

==========================================================
13. ДИАГРАММЫ И ВИЗУАЛИЗАЦИИ
==========================================================

Таблицы использовать только там, где они действительно нужны.

Предпочитать:

- KPI-карточки;
- progress bar;
- gauge;
- sparkline;
- timeline;
- heatmap;
- radar;
- mini chart;
- waterfall для PnL;
- matrix для стратегий;
- status ring для здоровья модели.

Запрещено:

- декоративные графики без смысла;
- 3D-графики;
- перегруженные таблицы на телефоне;
- графики без вывода для принятия решения.

Каждая визуализация должна отвечать на вопрос:
"Какое решение помогает принять этот элемент?"

==========================================================
14. ЦВЕТА И СТАТУСЫ
==========================================================

Цвет — это информация, а не украшение.

Базовая семантика:

Зеленый:
можно продолжать, статус нормальный.

Желтый:
нужно внимание.

Красный:
запрещено, ошибка, блокировка.

Синий:
идет процесс или наблюдение.

Серый:
нет данных, отключено, архив.

Статус должен всегда сопровождаться текстом.
Нельзя полагаться только на цвет.

==========================================================
15. КАРТОЧКИ
==========================================================

Карточка — базовый элемент Workspace V2.

Каждая карточка должна иметь:

- заголовок;
- главный показатель;
- статус;
- краткое пояснение;
- действие или переход к деталям.

Карточка должна корректно работать:

- на телефоне;
- на планшете;
- на desktop.

Карточка не должна содержать длинные технические таблицы.

==========================================================
16. ТАБЛИЦЫ
==========================================================

Таблицы допустимы только на уровне деталей.

На телефоне:

- таблицы должны заменяться карточками;
- либо иметь горизонтальную прокрутку;
- ключевые поля должны быть видны первыми;
- технические колонки скрываются по умолчанию.

Запрещено делать таблицу основным элементом Mission Control.

==========================================================
17. НАВИГАЦИЯ
==========================================================

Desktop:

- левая панель;
- рабочая область;
- status bar.

Планшет:

- компактная боковая навигация;
- 2 колонки.

Телефон:

- bottom navigation или drawer;
- Home;
- Back;
- ключевые разделы не более 5–7 пунктов.

Обязательные пункты навигации:

- Главная;
- Портфель;
- Бумага;
- Runtime;
- Research;
- Настройки.

==========================================================
18. PORTFOLIO WORKSPACE
==========================================================

Портфель должен показывать:

- капитал;
- денежные средства;
- открытые позиции;
- PnL;
- комиссии;
- риск;
- экспозицию;
- доступный риск;
- историю изменений.

Портфель должен иметь режимы:

- Paper;
- Shadow;
- Production.

Пользователь должен явно понимать, в каком режиме он находится.

==========================================================
19. БЕЗОПАСНОСТЬ UI
==========================================================

Запрещено:

- отправлять заявки из AI-слоя;
- менять runtime из информационных экранов;
- автоматически применять рекомендации;
- скрывать статус блокировки;
- показывать Production как доступный, если он заблокирован.

Любое действие, влияющее на систему, должно иметь:

- подтверждение;
- журнал;
- причину;
- откат или safe mode.

==========================================================
20. АРХИТЕКТУРНЫЕ ОГРАНИЧЕНИЯ
==========================================================

UI-патчи допускаются только в:

src/marketcore/presentation/
src/marketcore/ui/

Запрещено патчить UI в:

src/scripts/

Исключение возможно только для UI-сервера, если файл явно относится к presentation layer.

Backend ядра не переписывается ради UI.

UI не должен дублировать бизнес-логику.

UI читает готовые состояния и отображает их.

==========================================================
21. ОБЯЗАТЕЛЬНЫЕ ПРОВЕРКИ
==========================================================

Перед merge каждого UI Epic должны проходить:

1. UI Functional Audit.
2. Mobile Audit.
3. I18N Audit.
4. Responsive Audit.
5. Accessibility Audit.
6. No Raw Keys Audit.
7. Safe Target Audit.

Обязательные признаки успешного теста:

runtime_changed=0
execution_changed=0
orders_changed=0
fills_changed=0
micro_live_allowed=0

==========================================================
22. ACCESSIBILITY
==========================================================

Обязательные требования:

- достаточный контраст;
- читаемый размер шрифта;
- touch-элементы не менее 44 px;
- понятные подписи;
- не использовать только цвет для передачи смысла;
- кнопки должны иметь текст или aria-label;
- интерфейс должен быть usable на телефоне одной рукой.

==========================================================
23. КОНСТИТУЦИЯ ИНТЕРФЕЙСА
==========================================================

1. Интерфейс объясняет состояние системы.

2. Пользователь никогда не видит внутренние коды.

3. Главное состояние проекта понятно за один взгляд.

4. Любая критически важная информация доступна максимум за два клика.

5. Телефон — самостоятельный интерфейс.

6. Любая визуализация должна помогать принять решение.

7. Любое сокращение должно быть естественным и понятным.

8. Все строки проходят через i18n.

9. Все размеры, цвета и правила оформления централизованы.

10. UI не содержит бизнес-логики.

11. Backend ядра не переписывается ради UI.

12. Workspace V2 строится поверх существующей архитектуры.

==========================================================
24. ОБЯЗАТЕЛЬСТВО ПРИ РАЗРАБОТКЕ
==========================================================

Все новые экраны MarketCore Workspace V2 должны соответствовать настоящему стандарту.

Если предлагаемое UI-решение нарушает настоящий документ, оно должно быть отклонено или переработано.

Настоящий документ является обязательным ориентиром для всех последующих UI Epic.
